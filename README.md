# Overlord

複数のプロジェクトで、問題を見つけ、直し方を決め、実装し、確認する流れをAIと進めるための道具集です。

あなたは「何を先にやるか」「この直し方でよいか」「完成としてよいか」を決めます。AIは、気づきの整理、コードの調査、作業内容の整理、確認、進み具合の更新を担当します。

## 含まれるスキル

| Skill | 用途 |
| --- | --- |
| `product-ops` | 何を先に進めるかと、AIの作業状況を整理する |
| `product-improvement-card` | 気づきや問い合わせを、実行できる「やることカード」にする |
| `product-ux-audit` | 実際の操作の流れをたどり、使いにくい所を見つける |
| `product-implementation-brief` | 実装前に、何をどこまで変えるかを小さく整理する |
| `product-change-review` | 実装したAIとは別のAIが、目的どおり動くかを確認する |

## 設計

```text
気づき -> やることカード -> 順番を決める -> 実装前メモ -> 実装 -> 別のAIが確認 -> 完成の確認
                 |                                                    |
                 +---------- docs/product-ops/board.yaml ------------+
                                      |
                                      +-> Overlord Board Artifact
```

- `docs/product-ops/board.yaml` は、AIが次に何をするかを読む管理ファイルです。
- `Overlord Board` Artifactは、あなたが見るための分かりやすいダッシュボード画面です。
- 何かが進んだら、AIはまず管理ファイルを更新し、画面を使える環境ではダッシュボードも同時に更新します。
- 同時に実装するのは最大3件です。調査や確認も含めて、AIが抱える作業は10件前後までにします。

## ボードとArtifactの更新担当

`product-ops` が最初にAI用の管理ファイルと `Overlord Board` の画面を作ります。その後は、どのスキルを使っても、AIは管理ファイルを更新し、画面を使える環境ならダッシュボードも更新します。

| Skill | AI用の管理ファイルで更新する内容 | ダッシュボードで更新する内容 |
| --- | --- | --- |
| `product-ops` | 優先順位、進み具合、今日決めること | ダッシュボード全体、今日の判断、作業が多すぎる警告 |
| `product-improvement-card` | 新しいやること、問題の根拠、完成の条件 | 新しいカード、またはカードの詳しい内容 |
| `product-ux-audit` | 使いにくい所を「調査中」のカードとして追加 | 使いにくい所と、その大きさ |
| `product-implementation-brief` | どう直すか、どこを触るか、どう確認するか | 対象カードの実装準備の内容 |
| `product-change-review` | 確認結果、止まっている理由、完成確認の状態 | 対象カードの進み具合 |

通常のターミナルではダッシュボード画面を直接更新できません。この場合もAI用の管理ファイルは更新され、画面に反映する変更だけが `ARTIFACT_UPDATE` として返ります。

## Overlord Boardの見方

### 今日の判断

あなたがその日に決める必要があることだけを、最大3件表示します。ここに出るのは、AIだけでは決められないことです。

| 表示 | 意味 | あなたがすること |
| --- | --- | --- |
| 実装を承認する | AIが実装前の作業メモと、完成の条件を用意した | `進める`、`保留`、または直し方を変える |
| 改善案を選ぶ | 複数の解決案に有意な差がある | 採用する案を1つ選ぶ |
| 完成としてOKを出す | 実装と別のAIの確認が終わった | 実際の操作を確認して`受け入れる`または直しを指示する |

「次の一手」は、通常はAIが実行する作業です。あなたがタスクを作る必要はありません。

### ワークアイテム

ワークアイテムは、直したいこと、調べたいこと、確認したいことを表す1枚のカードです。1枚には、1つだけの小さな目的を入れます。

| 項目 | 意味 |
| --- | --- |
| ID | 例: `RC-UX-001`。会話、作業用の別フォルダ、確認結果を結び付ける番号 |
| 状態 | 受信箱、調査中、実装の準備完了、実装中、確認中、完成確認待ち、完了、停止中 |
| 大事さ | 効果の大きさ、急ぎ度、確かさ、簡単さを1〜5で付けた目安 |
| 担当 | 今作業しているAI、またはあなたの判断待ち |
| 次にすること | そのカードを進める、次の1つの作業 |
| 止まっている理由 | あなたの判断、ログイン情報、作業環境の問題など |

### ワークアイテムの中身

カードを開くと、AIが作業に使う情報を確認できます。

| 項目 | 内容 |
| --- | --- |
| 困っていることと根拠 | 何が起きているか、再現する手順、画面、利用者の声 |
| 原因の予想 | 確認できた事実とは分けて書く、原因の予想 |
| 選んだ直し方 | 何を変えるかと、その方法を選んだ理由 |
| 完成の条件 | 直ったと判断するために、実際に確認できること |
| 今回はやらないこと | 作業が広がりすぎないよう、今回触らない範囲 |
| 実装前メモ | 変更する場所、作業用の別フォルダ、動作確認、心配な点 |
| 確認結果 | 止めるべき問題、まだ確認していないこと、手で試す操作 |

## インストール

### Claude Code

個人用に入れる場合:

```bash
git clone <YOUR_REPOSITORY_URL>
cd overlord
./scripts/install.sh claude
```

プロジェクト単位で入れる場合は、対象リポジトリで実行します。

```bash
/path/to/overlord/scripts/install.sh project
```

Claude Codeは `.claude/skills/<skill-name>/SKILL.md` にある手順を読み込みます。起動後、`/product-ops` のように実行できます。

### Codex

```bash
git clone <YOUR_REPOSITORY_URL>
cd overlord
./scripts/install.sh codex
```

同じ名前のスキルがすでにある場合、インストーラーは安全のため停止します。更新するときは、今ある内容を確認してから入れ替えてください。

## 初期化

対象リポジトリのルートでClaude CodeまたはCodexを起動し、以下を実行します。

```text
/product-ops
このプロジェクトの作業管理を始めてください。
コード、今ある説明、プロジェクトの決まりを確認し、
docs/product-ops/board.yaml を作成してください。
最初に私が決めることは最大3件にしてください。
```

ダッシュボード画面を作れる環境では、同時に `Overlord Board` を作成・更新します。普通のターミナルでは画面を直接操作できないため、AI用の管理ファイルの更新と `ARTIFACT_UPDATE` の出力までを行います。

## 日常の使い方

### 気づきを残す

```text
/product-improvement-card
コール終了後に次の顧客へ進みにくい。保存できたかも分かりにくい。
今あるコードを確認して、やることカードにしてください。まだ直さないでください。
```

### 使用感を監査する

```text
/product-ux-audit
「顧客検索 -> 発信 -> 通話中メモ -> 終了処理 -> 次の顧客」を監査してください。
待ち時間、迷う所、間違って押しやすい所、失敗した後に戻れるかを確認してください。まだ直さないでください。
```

### 実装を始める

```text
/product-implementation-brief RC-UX-001
```

AIが作った実装前メモを確認し、問題がなければ実装を始めます。

```text
RC-UX-001を実装前メモに従って直してください。
1つのやることごとに別の作業用フォルダを使い、終わったら動作確認の結果と、まだ確認していないことだけを報告してください。
```

### 別のAIに確認してもらう

実装したAIとは別のAI、または新しい会話で実行します。自分で直したAIに、自分の変更を最終確認させないためです。

```text
/product-change-review RC-UX-001
```

いつものコード確認と、別のAIによる確認は見る場所が違います。

| 観点 | 通常のコードレビュー | Overlordの独立レビュー |
| --- | --- | --- |
| 主な目的 | コードが読みやすいか、決まりに合うかを確認する | 最初の目的を満たし、前から動いていた所を壊していないかを確認する |
| 見るもの | 主に変更したコードと周辺のコード | やることカード、実装前メモ、変更したコード、動作確認、実際の操作の流れ |
| 確認する人 | 実装の事情を知っている人でもよい | 実装したAIとは別のAI、または新しい会話 |
| 結果 | より良くする提案、読みやすさのコメント | 止めるべき問題、問題を起こす手順、完成の条件ごとの結果、手で試す操作 |
| 終わる条件 | 指摘を直し、チームの決まりに合う | 止めるべき問題がなく、完成の条件を確認できる |

別のAIによる確認は、いつものコード確認をなくすものではありません。コードの読みやすさはいつもの確認で見て、利用者の目的を満たすかは別のAIによる確認で見ます。

## 毎日の運用

朝に以下を実行し、あなたが決めることを最大3件に絞ります。

```text
/product-ops
今日の作業状況を整理してください。
私が決めることは最大3件、実際に試して確認する操作は最大3本に絞ってください。
各案件は次の一手を1つだけ示してください。
```

日中は気づきをやることカードにします。夕方は確認結果と、完成としてOKを出す前に試す操作だけを見ます。

## Artifactの扱い

Artifactはあなたが見る画面であり、AIが作業の順番を覚える場所ではありません。AIは常に `docs/product-ops/board.yaml` を読んで作業します。

画面とリポジトリの両方を扱える環境では、スキルが両方を同時に更新します。ターミナルだけの環境では画面を直接更新できないため、出力された `ARTIFACT_UPDATE` を画面を扱えるメインチャットへ渡してください。

## 変更と共有

チームで同じ作業表を使う場合は、プロジェクトへ `docs/product-ops/board.yaml` と `.claude/skills/` を保存してください。自分だけの順番を管理する場合は、`docs/product-ops/board.yaml` をGitで共有しない設定にしてください。
